# 01.7 — Phase 7: Restart, Continuation & Parallelization

**Purpose**: stop/restart long runs without losing progress, extend completed
runs, and use parallel hardware (CPU/GPU) efficiently.

## Checkpoints & exact restart

- `mdrun` writes a **checkpoint** (`state.cpt`, plus `state_prev.cpt`) on halt
  and periodically (`-cpt` interval, in **minutes**; `nstcheckpoint` in the MDP
  is obsolete and silently ignored in 2026.3).
- A checkpoint stores **full-precision** positions + velocities + all
  coupling-algorithm state (thermostat/barostat/λ) → an **exact** restart.
- Restarting from a `.gro` (with velocities) is **not** exact (lower precision,
  no coupling state).

```bash
# periodic checkpoint every 15 minutes (-cpt is in MINUTES, not steps)
gmx mdrun -deffnm md -cpt 15

# resume after a crash / preemption (-cpi alone = exact restart)
gmx mdrun -deffnm md -cpi state.cpt
```
- `-cpi` checkpoint in, `-cpo` checkpoint out (custom name).
- Query a checkpoint: `gmx check -f state.cpt`, `gmx dump -cp state.cpt`
  (**`-s` is not a `check` flag in 2026.3**; `dump` uses `-cp` for
  checkpoints, `-s` for `.tpr`).
- On each new checkpoint write, the old one is renamed `*_prev` → only recent
  progress can be lost to a write failure.

## Extending a completed run

1. **Preferred — `convert-tpr`** (change only run-control fields):
   ```bash
   gmx convert-tpr -s md.tpr -o md_ext.tpr -nsteps 10000000
   gmx mdrun -s md_ext.tpr -cpi state.cpt
   ```
   - `-nsteps <N>` sets an absolute step count; `-extend <time>` **adds** time
     (ps); `-until <time>` extends to an **absolute ending time** (ps) — use
     `-until` when you want "run until t = X" rather than "run N more steps".
     (`-nsteps -1` = unlimited.)
   - `mdrun -noappend` opens **fresh** output files (with a run-partition
     suffix) instead of appending to the existing `.xtc`/`.edr`/`.log` — use it
     when you want the continuation as a separate file set rather than one
     concatenated trajectory (the default is to append).
2. **Or regenerate the `.tpr`** with a new/edited MDP, then restart with
   `-cpi`. Some MDP options **cannot** change on a continuation (integrator,
   coupling scheme, topology) — regenerate cleanly if those must change.
- `tinit` / `init-step` control the starting time/step on restart.

## Re-running with the same `-deffnm`: the `#file.N#` trap

Re-running `gmx grompp`/`mdrun` in a directory where the outputs already
exist **auto-backs-up** the existing files to `#name.N#` (`#md.tpr.1#`,
`#md.xtc.2#`, …) and starts fresh `name.*` files. The dynamics are fine, but
the **file set fragments**, and it breaks `-cpi` resume:

- A `-cpi` resume writes to the **`-deffnm` output names** (`md.xtc`,
  `md.edr`, `md.log`) and is expected to continue the trajectory already in
  those files. (The checkpoint itself stores the simulation *state* — step,
  positions, velocities, coupling — not the output file names.) If the
  outputs were renamed to `#md.xtc.1#`, the resume creates *new* (empty)
  `md.xtc`/`md.edr` and appends the continuation there — the trajectory is now
  split across `#md.xtc.1#` + `md.xtc`, and any analysis reading `md.xtc`
  silently sees only the tail.
- `mdrun -noappend` writes `md.part0001.*` (a deliberately separate file set)
  — fine for "continuation as separate files", but do **not** combine it with
  `-cpi` resume semantics that expect to append to the original names.

Rules:
1. **Fresh re-run** (e.g. after editing the MDP): use a **new** `-deffnm`
   (e.g. `md2`) so the old outputs stay intact, or move the old outputs out
   of the directory first.
2. **`-cpi` resume**: requires the original `name.xtc`/`name.edr`/`name.log`
   to be intact under their original names. If they are `#…#`-backed-up,
   restore them (or use a new `-deffnm` and accept a fresh file set).
3. Never assume `name.xtc` is the whole trajectory — after any re-run with a
   reused `-deffnm`, check for `#name.*.N#` siblings before analyzing.

## Are continuations exact?
- Yes, **if** you restart from a checkpoint with the **same** `.tpr` (same
  integrator, coupling, topology, and ideally same rank count). Changing the
  rank count or algorithm can introduce tiny floating-point differences
  (not bit-identical, but physically equivalent).

## Reproducibility
- Same GROMACS **binary** + same `.tpr` + same rank count + same algorithm →
  reproducible trajectory.
- Different hardware / rank count / FFT library → generally **not**
  bit-reproducible (expected; floating-point non-associativity).

## Parallelization model

GROMACS parallelizes over three levels:
1. **Intra-core SIMD** (SSE/AVX/AVX-512) — automatic.
2. **OpenMP threads** (`-ntomp`) — within a node/core group.
3. **MPI ranks** (`-ntmpi`) — across cores/nodes, via **domain
   decomposition**.
4. **GPU offload** — `nb` (non-bonded), `pme`, `bonded`, `update` tasks to the
   GPU.

### Key flags

| Flag | Meaning |
|------|---------|
| `-ntmpi N` | MPI ranks (domain-decomposition partition count). |
| `-ntomp N` | OpenMP threads per rank. |
| `-nt N` | Total threads (mdrun partitions into ntmpi×ntomp). |
| `-nb gpu` | non-bonded on GPU. |
| `-pme gpu` | PME (reciprocal electrostatics) on GPU. |
| `-bonded gpu` | bonded forces on GPU. |
| `-update gpu` | coordinate update + constraints on GPU. |
| `-npme <N>` | dedicate N ranks to PME (multi-node, large systems; default -1 = guess) |

### Domain decomposition
- The box is partitioned into cells assigned to ranks; particles communicate
  across cell boundaries.
- **Minimum cell size** is set by the largest charge group / bonded group and
  the largest of `rvdw`/`rlist`/`rcoulomb` (+ safety margin). A system too
  small for `n` ranks → `no domain decomposition for n ranks ...` error.
  Reduce ranks or split large charge groups.
- **Dynamic load balancing** rebalances cells to equalize work.

### GPU-resident update (this stack — gfx1100/HIP)
Requirements:
- `-ntmpi 1` (single rank) — domain decomposition is incompatible.
- A **dynamical** integrator (`md`/`sd`), not `steep`/`cg`.
- System must have classical bonded interactions (pure SETTLE water has none).
- **Performance-recommended** (not required): `constraints = h-bonds`, not
  `all-bonds` — `all-bonds` works but adds P-LINCS communication overhead.
- **Incompatible** with: free-energy perturbation, domain decomposition,
  replica exchange.
Full offload:
```bash
gmx mdrun -ntmpi 1 -nb gpu -pme gpu -bonded gpu -update gpu -deffnm run
```
Confirm in the log: `PP task will update and constrain coordinates on the GPU`.

## Performance checklist (→ `03.5`)
- Match rank/thread counts to hardware; don't over-partition small systems.
- Put `nb`+`pme` on GPU for large systems; `update`+`bonded` on GPU when
  constraints allow.
- Check the log's performance summary + `gmx nonbonded-benchmark` (the old
  `gmx benchmark` is gone; see `00.1`).
- Avoid features that force CPU fallback (see above).

## Common errors (→ `01.9`)
- `no domain decomposition for n ranks ...` — too many ranks for the box /
  large charge group.
- `One or more atoms moved too far between two domain decomposition steps` —
  blowing up.
- Restart "starts from time zero" — set `tinit`/`init-step` (and restart from
  a checkpoint with `-cpi`).

## Validation criteria
- [ ] Restart resumes at the correct step/time (check log).
- [ ] Continuation is exact (same tpr + checkpoint).
- [ ] No `#file.N#` fragmentation: the `-deffnm` outputs are a single
      contiguous set (check for `#name.*.N#` siblings before analyzing).
- [ ] Parallel config is valid (no DD error) and GPU offload engaged (if used).
- [ ] Performance reasonable (check summary; `03.5`).

## Outputs
Extended/continued trajectory + energy (appended), new `state.cpt`, and a
documented parallel configuration.
