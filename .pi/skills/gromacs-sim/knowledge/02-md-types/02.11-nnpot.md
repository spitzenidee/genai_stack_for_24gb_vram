# 02.11 — Neural-Network Potentials (NNP)

> **Not available on this stack's build** (`Torch support: disabled`).
> Requires a LibTorch-enabled build (`-DGMX_NNPOT=TORCH`). The notes below
> apply once enabled.

**When to use**: run MD with a **machine-learned potential** (neural-network
potential) instead of a classical force field — where a trained model gives
QM-like accuracy at (near) MD speed. GROMACS 2026 ships the **NNPot** module.

## What NNPot is
- A module that lets GROMACS use an **external neural-network potential** to
  compute energies and forces during the simulation.
- The NNP is trained (offline) on a dataset (e.g. DFT data) for the system of
  interest, then loaded into GROMACS at run time.
- **2026.3 API**: NNPot is a **module** named `nnpot`, enabled with flat MDP
  options (the module is registered in this build, but activation aborts at
  **grompp** time because LibTorch is not linked — see the banner above):
  ```
  nnpot-active = yes
  nnpot-modelfile = model.bin    ; trained model file (LibTorch format)
  nnpot-input-group = NNP        ; index group of atoms the NNP acts on
  nnpot-pair-cutoff = 1.2        ; pairlist cutoff for the model
  nnpot-embedding = mechanical   ; mechanical | electrostatic-model
  nnpot-link-type / nnpot-link-distance  ; boundary capping (link-type = element symbol)
  nnpot-model-input1..9          ; extra per-model inputs (e.g. nnp-charge)
  ```
  **This build**: activating NNPot aborts at **grompp** time (not mdrun
  runtime) with
  `Libtorch/NN backend is not linked into GROMACS, NNPot simulation is not
  possible. Please, reconfigure GROMACS with -DGMX_NNPOT=TORCH`.
  (`nnpot-mm-group` and `nnpot-nnp-charge` are **not** valid options in this
  build; the NNP net charge is set via an `nnpot-model-input` field, per the
  manual.)

## When it's the right tool
- You need **electronic-structure-level accuracy** (reactions, polarizability,
  unusual chemistry) but can't afford on-the-fly QM/MM (`02.10`) for the whole
  run.
- A **validated** NNP exists for your element set / chemistry.
- You want long timescales with better transferability than a hand-built FF.

## Setup outline
1. **Obtain/train** a validated NNP for the system (outside GROMACS).
2. **Prepare** the system as usual (`01.1–01.3`) — the NNP defines the
   potential; the topology still describes atoms (and often a minimal bonded
   set, depending on the model).
3. Set the **NNPot MDP options** (`nnpot-active = yes`, `nnpot-modelfile`,
   `nnpot-input-group`, `nnpot-pair-cutoff`, ...) and ensure the atom set
   matches what the model was trained on.
4. **Validate**: run a short test and compare NNP energies/forces to the
   reference (DFT) on a few frames; confirm stability.
5. Equilibrate + production as standard.

## Practical notes
- **Model validity**: an NNP is only as good as its training data — check the
  element set, charge states, and environment coverage. Extrapolation outside
  the training domain is unreliable.
- **Cost**: much cheaper than QM/MM, but more expensive than a plain FF (model
  evaluation per step).
- **Reproducibility**: pin the model file/version; report the model + training
  source.

## MDP deltas vs. standard
- Add the **`nnpot-*` options** (`nnpot-active = yes`, `nnpot-modelfile`,
  `nnpot-input-group`, `nnpot-pair-cutoff`, `nnpot-embedding`, ...).
- Otherwise standard ensemble/integrator settings.

## Analysis
- Standard (`01.8`) on the trajectory.
- Cross-check a subset of energies/forces against the reference method.

## Pitfalls
- Using an NNP **outside its training domain** → silently wrong physics.
- Mismatch between the topology's atom set and the model's expected atoms.
- Forgetting to **validate** against the reference before a long run.
- Not reporting the model provenance (training data, version) → irreproducible.
- NNPot is a **newer** module — check the current release notes for exact
  option names and supported model formats (→ `00.1`).
