# GROMACS KB Audit

Validate every claim in the GROMACS knowledge base against the locally running
GROMACS build, and document findings in `issues_kb.md`. Fixes happen in a
separate session by a separate worker; your issue entries are their work list.
Everything (build snapshot, claim lists, probe verdicts) is regenerated from
live sources on every run — nothing KB-derived is stored in this skill.

## Paths

| What | Where |
|---|---|
| Stack root | `/home/<user>/docker/genai_stack` (a git repo — used for drift scoping) |
| Knowledge base | `.pi/skills/gromacs-sim/knowledge/` — content files (00–03) + `README.md` + `issues_kb.md` |
| Issues log | `.pi/skills/gromacs-sim/knowledge/issues_kb.md` — the **only** file you may write |
| Container access | transient, CPU-only (no GPU devices ever passed): `docker run --rm -w /work -v $STACK_ROOT/gromacs/work/kb-audit:/work gromacs-hip-gfx1100:latest <cmd>` — works in any stack mode, at any time; no running container needed |
| Session dir | `gromacs/work/kb-audit/` (= `/work` in the transient container) — wiped and regenerated by the suite at the start of every run; shared with the fixer skill; no cross-run persistence |

## Hard rules

1. **Validate only.** Never edit any KB file. The only file you may write is
   `knowledge/issues_kb.md` (append a new dated section). "Recommended fix"
   text lives inside the issue entry, not in the KB.
2. **No GPU work.** `mdrun` / `nonbonded-benchmark` are **forbidden**; probes
   are CPU-only (`grompp`, `gmx <tool> -h`, `find`, `strings`, `ls`) —
   enforced by construction: the transient container is never passed GPU
   devices. Exception: claims needing runtime output files may use a short
   CPU-only run (small box, ≤ 1000 steps, `-nb cpu -pme cpu`), flagged in the
   report. When in doubt: "unverified — needs GPU".
3. **The build is the gold standard.** `manual.gromacs.org/current` is *newer*
   than the local build; where docs and build disagree, **the build wins**.
   For semantics use the version-pinned manual (`manual.gromacs.org/<version>`)
   and the `v<version>` source tag.
4. **Verbatim evidence.** Every issue quotes the exact build output (error
   text, grompp NOTE, `-h` line, `gmx dump` line) that proves it.
5. **Don't poke in the dark.** If a claim has no probe in the suite, add the
   probe to `scripts/probe_suite.sh` (probe assets + their traps: `assets/`)
   and keep the suite self-healing. Ad-hoc probing is a last resort; the
   suite is the default.
6. **Never switch the stack mode.** The agent's own LLM compute runs on the
   eGPU in the current stack mode; switching modes (`make gromacs` — or any
   `make <mode>` in the stack root, `scripts/switch-mode.sh`,
   `docker compose up --profile gromacs`) tears it down mid-session: a
   rugpull of your own compute. No GROMACS work ever requires a mode switch:
   all commands run in transient `docker run` containers, CPU-only (no GPU
   devices passed), in any mode, at any time. If the image is missing, stop
   and tell the user — building the image needs no mode switch.

## The run

### Step 1 — Probe suite (deterministic)

```bash
bash <skill-dir>/scripts/probe_suite.sh
```

Self-contained: every probe runs in a transient `docker run` container
(hard rule 6) — no preconditions beyond the built image.

Produces in the session dir:
- `snapshot/` — `fingerprint.txt`, `00_version.txt`, `01_commands.txt` +
  `01_command_names.txt`, `02_help/<tool>.txt` (every tool),
  `03_ff_listing.txt`, `04_envvars.txt`, `05_install_tree.txt`,
  **`03_block_verdicts.txt`** (one verdict line per KB MDP block, with
  details for failing ones), **`03_matrix_verdicts.txt`** (merged existence
  check), **`06_directive_verdicts.txt`** (one verdict line per unique
  topology directive: name check + usability).
- `claims/` — mechanical extraction from the **live** KB:
  `mdp_options_raw.txt` (every `option = value` claim, file:line),
  `mdp_options_unique.txt`, `mdp_multi_value.txt`, `blocks_manifest.txt`,
  `cli_commands.txt`, `cli_tools.txt`, `directives_raw.txt` (every
  `[ directive ]` claim, file:line + inferred context),
  `directives_unique.txt`, `notes.txt` (stats + scope +
  false-positive classes — read it).
- `blocks/block_NNN.mdp` + `.log` — each KB fenced MDP block probed as-is
  (a context header adds only options the block lacks).
- `matrix/base.mdp` + `.log` — merged existence matrix.
- `directives/<name>_{a,b}.{top,log}` — per-directive name (a) and usability
  (b) probes; `ctl_bad`/`ctl_good` are the self-healing controls.

Probe model: **block** verdicts = each KB MDP block probed in its own
context; the **matrix** = consolidated existence index. Stale matrix rows are
harmless (superset probe); only *missing* rows matter (hard rule 5).

Drift scoping (before reading anything):
- `snapshot/fingerprint.txt` vs the "Gold standard" header in `issues_kb.md`
  → build changed? Note it at the top of the new section; expect more findings.
- `git -C /home/<user>/docker/genai_stack diff --stat HEAD -- .pi/skills/gromacs-sim/knowledge/`
  → optional focus hint only: it shows *uncommitted* working-tree changes
  (a commit-agnostic one-shot; nothing is recorded). It is **never a scope** —
  every pass is a full pass: read all files, map every claim, file on any
  failure. A clean diff means nothing about the outcome; do not relax scrutiny.

### Step 2 — Read the KB

Read `knowledge/README.md`, then all content files in order
(`00-foundations` → `01-phases` → `02-md-types` → `03-playbooks`), hunting
**semantic claims** the mechanical extraction cannot see: prose about
behavior, compatibility, ensembles, capabilities ("MTTK requires md-vv", …).
Mechanical claims are already in `claims/` — verify they match what you read,
don't re-derive them.

**Topology directive *names* are mechanically probed**
(`06_directive_verdicts.txt`); this read covers what the probe cannot see:
directive *content* (column order, nrexcl values, atom-type references) and
*placement* semantics. Watch the molecule-vs-top-level distinction:
`[ bonds ]`/`[ angles ]`/`[ dihedrals ]` live *inside* a `[ moleculetype ]`;
`[ bondtypes ]`/`[ angletypes ]`/`[ dihedraltypes ]` are *top-level* tables —
the two are different directives and are easy to confuse. A `B=order`
verdict means the name is known but unusable at the canonical position
(top-level tables, `molecules`); judge placement in prose against the
context the KB claims.

`issues_kb.md` — read targeted, not whole: Gold-standard header + latest
pass section + last I-NN; grep the rest for open (non-`RESOLVED`, non-`FALSE POSITIVE`) issues and
re-verify those first (if the KB already reflects a fix, note "ready to close
by the fixer" — do not mark resolved). Verified-OK lists: spot-check only.

### Step 3 — Map claims to the snapshot

Every claim gets a verdict: **OK** or **issue**.
- MDP options → `snapshot/03_block_verdicts.txt` (the claim's block, probed in
  its own context), then `03_matrix_verdicts.txt` / `matrix/base.log`
  (consolidated), then `blocks/block_NNN.mdp.log` (verbatim lines).
- Multi-value options (`claims/mdp_multi_value.txt`) → targeted single-option
  value probes (rubric below).
- CLI tools/flags → `snapshot/02_help/<tool>.txt` (the build's own `-h` text). **Grep the snapshot file in the outer shell** (`grep -E '^[[:space:]]*-<flag>([[:space:]]|\[)' snapshot/02_help/<tool>.txt`); do **not** run an inline `docker run … bash -c "grep … $var"` loop — the loop variable does not survive into the inner shell, the pattern silently degrades to a match-all, and every flag reads "present" (a false negative for the audit).
- Tool existence → `snapshot/01_command_names.txt`.
- Topology directives → `snapshot/06_directive_verdicts.txt` (name +
  usability per unique name), then `directives/<name>_{a,b}.log` for verbatim
  parser output.
- FF/water → `03_ff_listing.txt`; env vars → `04_envvars.txt`; install tree → `05_install_tree.txt`.
- Semantic claims → reproduce in the build (a probe that triggers the exact
  error/NOTE), then version-pinned manual / source tag.
- Error-string claims (KB quotes an error/warning message) → **reproduce the
  error with a targeted probe first** (that is the gold-standard verdict).
  `strings` on `libgromacs.so` is a fallback, not a verdict: messages are
  often format strings (`%d`/`%s`/`%g` args never appear in the binary —
  grep a stable word fragment, e.g. "longer than", not the rendered
  "4095"), and case must match exactly ("Range checking" ≠ "Range
  Checking"). A batch `strings` sweep is a screening tool only — a
  strings-only verdict (either direction) is not a verdict: confirm by
  targeted reproduction before filing; near-duplicate variants in the
  binary make a strings hit ambiguous (it proves existence, not which code
  path emits it). If reproduction needs `mdrun`, file the issue flagged
  "unverified — needs a run". An ABSENT verdict requires a fragment +
  case-insensitive binary sweep *and* a failed reproduction attempt. The source tag is only
  supplementary — a dev-snapshot build may differ from the release tag.
- Claim with no snapshot coverage → add the probe (hard rule 5), re-run just
  that part, record the verdict.

### Step 4 — Document issues

Append one new section to `knowledge/issues_kb.md` per
`references/issue_format.md`: continued I-NN numbering, severity, `Files:`
list, verbatim evidence, **Recommended fix** (not applied), closing
**Verified OK** list and **Notes**. Append only.

### Step 5 — Report

Issues by severity with one-line titles; affected files; regression results;
unverified-needs-GPU items; handoff note that the new `issues_kb.md` section
is the fixer's complete work list.

## Reading probe output (grading rubric)

**Block verdict lines** (`03_block_verdicts.txt`):
`block_NNN.mdp (kbfile:lines) exit=N unknown=N invalid=N obsolete=N errors=N notes=N`
- `unknown`/`invalid`/`obsolete` > 0 → **parse signal** — the KB block uses an
  option/value the build rejects. Read the details section (appended below the
  line) and the block log; file an issue unless it is a known false positive.
- `errors` > 0 with `unknown`/`invalid` = 0 → usually **system noise** from
  probing a 1-atom dummy system (topology limits, `-nan K` Verlet buffer,
  AWH/com-pull incompatibility, exit=139 on exotic MD types). Not an issue by
  itself; read the log to be sure it is not masking a parse problem.
- `notes` > 0 → check: legacy-alias/deprecation NOTEs **are** findings
  (`[M]`); zero-step/single-point-energy NOTEs are expected, not findings.

| What the probe shows | Meaning |
|---|---|
| `Unknown left-hand` / unknown command | option/tool absent — or context-dependent (the block lacks its parent: re-probe with the parent enabled, then file) |
| `Invalid enum 'X' for variable Y` | option exists, value wrong; authoritative enum = pinned manual / source / `gmx dump` of a TPR with a good value |
| `NOTE …` (legacy alias, deprecation) | `[M]` — quote it verbatim |
| `Ignoring obsolete mdp entry 'X'` | option parses but is **silently dropped** — never reaches the TPR. This is an issue, not OK. Confirm with `gmx dump -s <tpr>` (no positional arg in this build) |
| `Too many warnings` | grompp aborted; unknown options are *warnings* — `-maxwarn` would silently ignore them (a silent no-op run). Note this failure mode in relevant issues |
| grompp exit 0 + option in `gmx dump` output | **OK** — the only clean verdict |
| `Invalid directive X` (stage A, `06_directive_verdicts.txt`) | X is **not a directive in this build** (misspelled/renamed/removed) — issue |
| `Invalid order for directive X` (stage B) | X is known but unusable at the canonical position (context-restricted, e.g. top-level tables / `molecules`) — judge against the context the KB claims |

**Directive-probe traps (2026.3, verified):** an *unknown* directive at the
end of a moleculetype is **silently ignored** (grompp exit 0) — never judge a
name from a stage-B/end-of-moleculetype result; stage A (line 1) is the only
name check. An unknown directive followed by a known one at top level can
surface as `Invalid order for directive <next>` — read the whole log when
probing ad hoc.

**Known false-positive classes**: see `claims/notes.txt` (regenerated every
run) — read it before filing; judge each hit by its file:line reference.

Severity: `[H]` breaks a workflow / wrong result · `[M]` stale name, needs
update · `[L]` cosmetic / doc-only.

Context parents for re-probes (verified against this build): `pull = yes`
(+`pull-ncoords`/`pull-ngroups`), `awh = yes`, `free-energy = yes` (FEP) /
`expanded` (LMC), `nnpot-active = yes` (build aborts without LibTorch — probe
*names* only), `colvars-active = yes`, `coulombtype = FMM`. `awh = on` and
`free-energy = alchemical-decoupling` are **invalid enums** here — a KB claim
using either is itself the finding.

Targeted value probe: copy `assets/base.mdp` (verified minimal MDP) into the
session dir, add the option in question, run grompp in the transient
container (Paths table) — `Invalid enum` names the valid values.

## Planning discipline

- **Todo list is the tracker**: one task per KB document +
  `run probe suite`, `read issues_kb.md + drift check`,
  `document issues`, `report`. One task in_progress at a time; mark completed
  immediately.
- **Sequential thinking**: run a `sequential_think` pass only if the build
  changed since the last audit or ≥3 claims have no clear rubric verdict;
  otherwise todo list + rubric suffice. Use `process_thought` for ambiguous
  build output (NOTE vs error, alias vs rename, obsolete-but-parsed).
- **Resuming across sessions**: todo list + a WIP-marked section in
  `issues_kb.md` are the state. Re-run the probe suite first — it wipes and
  regenerates the session dir, so never trust stale contents — then read the
  WIP section and continue.
